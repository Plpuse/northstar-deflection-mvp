# 🚀 Team Charter — Team Northstar

## 1. Team Purpose & Vision
* **Mission:** Build and ship a functional, well-tested Deflection MVP that handles automated user queries (such as order status lookups and return policy decision trees) efficiently.
* **Goal:** Maintain high code quality, follow standard commit conventions, and foster active group collaboration through peer code reviews.

---

## 2. Roles & Responsibilities

* **Keisha Ochieng (Team Administrator / Lead):** Coordinates repository structure, manages issue boards, assigns sprint tasks, and oversees workflow execution.
* **Dennis, Kutere, Sarah, Plpuse (Collaborators / Developers):** Author feature/documentation branches, write modular code and schemas, open PRs, and perform mandatory peer code reviews.

---

## 3. Communication & Working Agreements

* **Primary Communication:** WhatsApp / Slack group chat.
* **Check-ins:** Daily asynchronous status updates regarding progress, potential blockers, or pending pull requests.
* **Response Expectations:** Team members agree to acknowledge messages and review tagged PRs within **12–24 hours** on active sprint days.

---

## 4. Workflows & Contribution Guidelines

* **Branch Strategy:** No direct commits to the `main` branch. All work must be conducted on dedicated branches (e.g., `feat/<feature-name>`, `docs/<doc-name>`, `chore/<task-name>`).
* **Commit Message Format:** All commits must follow conventional naming standards:  
  `<type>: <short description> - <why it matters>`  
  *(Example: `feat: add return policy decision tree - enables automated return checks`)*
* **Issue Linking:** Every PR description must link back to its corresponding issue card using `Closes #X` or `Fixes #X`.

---

## 5. Definition of Done (DoD) & Review Process

Before any Pull Request is approved and merged into `main`, it **MUST** satisfy the following:
- [x] **Functionality / Accuracy:** The code, schema, or documentation matches the issue requirements.
- [x] **Verification / Testing:** Includes proper test cases, sample data, or manual validation notes.
- [x] **Peer Review:** Requires **at least 1 approving review** from a fellow team member on GitHub.
- [x] **Ownership & Tagging:** The PR author assigns themselves under **Assignees** in the sidebar.

---

## 6. Decision Making & Conflict Resolution

* **Open Discussion:** Decisions on technical implementation or task distribution will be discussed openly in the team chat.
* **Consensus & Voting:** If disagreements arise, the team will vote. In the event of a tie, the Team Administrator facilitates the final decision to keep the project moving forward.
* **Constructive Culture:** All pull request reviews and team communications must remain direct, respectful, and supportive.
